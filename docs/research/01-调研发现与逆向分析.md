## 1. 项目背景与现状

业务链路：**上游 netshort（短剧 CPS 平台）→ 我方处理 → 下游供应商**。

前开发者（下称"前开发"）留下的可运行资产只有一个浏览器端 HTML 看板，但它同时揭示了一个**未交付代码、仍在运行的自建后端**（api.tfctechnology.com）。整体架构：

```
上游 netshort CPS API（飞书文档这套，8 个接口）
        │
        ▼
前开发的自建后端（api.tfctechnology.com，代码拿不到）← 供应商应调用的就是这套
  · POST /auth/login            账号登录
  · POST /data/partner/order/report   过滤后的订单报表
        ▲
        │ 同时直连上游（HTML 内硬编码上游 client secret，做"已过滤 vs 全量"对账）
HTML 看板（浏览器端，纯静态单文件）
```

看板核心业务模型：**双源对账 + 双档分成**。

- 同一天的订单查两次：老后端报表（已过滤）一次、上游全量一次；
- 上游有、报表没有 →「缺失订单」，按 **70%** 分成；
- 报表里有 →「已过滤订单」，按 **20%** 分成（代码 `visualisation(1)(1).html:427`：`SHARE = { included: 0.20, excluded: 0.70 }`）；
- 另加每日广告收入（上游 `/open/order/adSummary`，"该渠道纯新用户"口径）。

## 2. 上游开放接口清单（飞书文档 v1.2.0）

环境：测试 `https://adminapi.test.netshort.net/test-api/cps/`，商用 `https://adminapi.netshort.com/prod-api/cps/`

鉴权：推荐 OAuth 2.0 Client Credentials（换票 `POST /open/oauth2/token`，支持 HTTP Basic 或 form 凭证，Bearer 调用业务接口，token 默认 3600 秒）；MD5 签名仅兼容存量。统一响应信封 `{code, msg, data, traceId}`。

| 1 | `/open/oauth2/token` | POST | 不校验 | 换取 Access Token |

## 4. 老后端逆向：已确定的行为

以下结论全部由 HTML 代码与注释直接支撑，**可作为重写规格**。

### 4.1 已确定（100% 置信）

| # | 行为 | 证据 |
|---|---|---|
| 1 | **上游密钥托管**：后端持有 `PARTNER_CLIENT_ID/SECRET`，OAuth 换票、缓存、到期前 ~60s 刷新、401 丢缓存重换并重试一次 | HTML:445-447 注释"mirroring partner-adapter/partner_client.py"；HTML:880-944 为其前端镜像 |
| 2 | **字段改名**：上游订单的美元字段 `orderAmount` 改名为 `usdOrderAmount`；其余字段（orderId, createTime, theaterId, chapterId, language, currencyType, amount, refundTime, promotionCode）原样透传 | HTML:745-754 注释 |
| 3 | **100 行硬截断 + hasMore**：无论 pageSize 传多大（前端传 1000）最多回 100 行；返回 `hasMore` 标志（上游本身无此字段）；`page` 参数形同虚设 | HTML:431、948-950 |
| 4 | **汇率处理演变**：旧方案为静态汇率表（`export_orders.py` 的 USD_RATES，约 30 币种、2026-08 估值，无汇率币种直接丢弃不计入）；新方案直接用上游自报美元额。前端复刻了旧表用于"旧 vs 新"对比卡 | HTML:756-779 |
| 5 | **自有账号体系**：JSON 传 username/password → 返回 `{access_token}`；401/403/422=凭证错；业务接口 Bearer；统一 R 信封 `{code, msg, data}`，`code≠200` 即业务错误。`REDACTED-USER/REDACTED-PASSWORD（值已抹除）` 为其中一个账号 | HTML:463-466、831-870 |
| 6 | **未在后端做的**（全在前端）：双源对账 diff、20/70 分成计算、按日/币种/国家聚合、language→国家推断、退款识别（refundTime 非空）、CSV 导出、adSummary 代理（前端拿上游密钥直连） | HTML 各渲染函数 |

### 4.2 老后端接口契约（重写时的兼容规格）

**`POST /auth/login`**
```
请求: {"username": "...", "password": "..."}
  200 → {"access_token": "..."}
  401/403/422 → 凭证错误
```

**`POST /data/partner/order/report`**（Header: `Authorization: Bearer <token>`）
```
请求: {"startDate": "YYYY-MM-DD HH:mm:ss", "endDate": "…", "page": 1, "pageSize": N}
响应: {"code": 200, "msg": "…", "data": {"list": Order[≤100], "hasMore": bool}}
Order = {orderId, createTime, theaterId, chapterId, language, currencyType,
         amount, usdOrderAmount, refundTime, promotionCode}
```
内部管道 = 换票 → 调上游 `/open/order/list` → **过滤（规则黑盒，见 §5）** → 字段改名 → 截断 100 行。

### 4.3 黑盒（推断不出，见 §5 与待确认清单）

**订单过滤规则本身**——决定哪些订单进报表（计 20%）、哪些被剔除（计 70%）。

## 5. 过滤规则数据分析

### 5.1 数据集

14 天（2026-09-29 ~ 10-12）全部订单导出，共 **6,016 笔**；12 分钟后刷新重导一次复测。

| 分类 | 笔数 | 占比 | 订单总额(USD) | 分成比例 | 分成收入 |
|---|---|---|---|---|---|
| 已计入 | 4,824 | 80.2% | $64,444.34 | ×20% | $12,898.38 |
| 被剔除 | 1,192 | 19.8% | $16,389.41 | ×70% | $11,469.09 |
| 合计 | 6,016 | 100% | $80,833.75 | — | **$24,367.47** |

**被剔除订单仅占笔数 19.8%，却贡献 47.1% 的分成收入**——这就是该看板存在的意义（只看老后端报表会漏掉近一半收入）。

### 5.2 排除的假设（全部检验过，均无规则）

| 维度 | 检验结果 |
|---|---|
| 币种（30 种）/ 国家（15+）/ 语种 | 剔除率全在 16~23%，无差异 |
| 短剧 ID（16 部） | 无规则（2 部轻微偏离，过不了多重检验校正） |
| 金额 / 逐币种价格点 / 中位金额差 | 无规则（$2.00 差异，置换检验不显著） |
| 时段（24h）、小时交易量 | 无规则（r=-0.198 不显著） |
| 退款滞后回溯删除 | 无日期梯度，排除 |
| 订单号取模/MD5 哈希采样 | 无规则（订单号低 4 位 99.7% ∈ {1,2} mod 16，为 ID 生成器结构） |
| 订单号连串 / 时间桶内位置（同步丢尾） | 平均串长 1.29 ≈ 随机期望 1.25，位置均匀，排除 |

### 5.3 三个真实信号

1. **退款单被剔除率 38.6%（57 笔中 22 笔），是正常单的 2 倍**（z≈3.6，p<0.001）→ 分类与退款概率相关，说明背后是真实属性而非随机；
2. **窗口头两天（9/29-30）剔除率 25.4% vs 其余 19.1%**（z=+3.89）→ 逐日卡方 32.8（df=12，p<0.01），日间存在真实结构（待确认是真实期段效应还是抓取边界效应）；
3. **分类完全确定**：刷新后 12 分钟重导，6,016 笔共有订单**类别翻转 0 笔**、状态/金额变化 0 笔；新增 11 笔当日订单（9 计入 / 2 剔除，80/20 延续）→ **排除"查询时随机"**。

### 5.4 结论

过滤依据的是**两边接口都不暴露的隐藏属性**。三种情形判别：

| 情形 | 机制 | 判定 |
|---|---|---|
| A. 查询时随机 | 每次请求重抽 ~80% | ❌ 已排除（复测 0 翻转） |
| B. 入库时随机丢一次 | 历史凝固 | 基本排除（解释不了退款 2 倍相关性） |
| **C. 隐藏确定性规则** | 上游归属/结算口径或用户类型（如新客/复购）等未暴露字段 | ✅ **当前最优解释** |

最可能的业务含义：20% 档 = 上游正式归属/结算给本渠道的常规 CPS 佣金；70% 档 = 推广码名下但未进正式报表订单的特殊约定分成（合同口径待确认，见待确认清单）。

### 5.5 附带发现

- **上游时间疑似 UTC 且有滞后**：两次导出中"最新订单时间"都比本机时间早约 8 小时（01:26 ≈ 北京 09:26），且存在约数十分钟级同步延迟 → 看板"今天"的数据永远不全，完整数据要次日看；
- 上游分页无 hasMore，前端以"整页返回"判定可能截断（请求 pageSize=1000）；
- 老后端报表 100 行截断迫使前端做时间窗二分（HTML:950-983），是接口设计缺陷，重写时应改真分页。

## 6. 安全风险（高优先级）

1. HTML 内**明文硬编码**：上游 `client_id=client_tfc_[值已抹除]` + `client_secret`（HTML:458-462）、老后端账号 `REDACTED-USER/REDACTED-PASSWORD（值已抹除）`（HTML:463-466）。**任何拿到该文件的人可直连上游数据**。该文件已在多人间流转（含下载副本），应视为已泄露，建议尽快轮换上游密钥与后端账号；
2. 前端直连上游意味着若把此 HTML 发给供应商，等于把上游密钥发给每个供应商；
3. 重构后的硬性要求：上游密钥仅存服务端，前端只访问我方后端。
