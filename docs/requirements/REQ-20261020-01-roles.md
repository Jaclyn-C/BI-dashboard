# REQ-20261020-01 · 角色权限（内部 / 客户身份与审批分配）

> 状态：已确认（用户 2026-10-20 会话定稿，含角色调整等级规则）
> 背景：认证三件套（REQ-20261012-01）已上线，当前所有登录用户权限相同。本需求引入角色：
> 自己人（管理员）看全部，下游客户只看客户看板，新注册用户需管理员分配权限后方可使用。

## 1. 需求内容

### 1.1 角色定义（3 角色 + 待分配态）

| 角色 | 数量 | 可见范围 | 用户管理权限 |
|---|---|---|---|
| `super_admin` 超级管理员 | 全系统仅 1 个 | 全部页面 | 可调整任何其他用户 |
| `admin` 管理员 | 自己人（约 ≤10） | 全部页面（含客户视图、用户管理） | 仅可调整客户 / 待分配用户 |
| `customer` 下游客户 | — | 仅客户视图 | 无 |
| `pending` 待分配（注册默认态） | — | 仅「等待分配」提示页 | 无 |

- **不提供删除账号功能**：用户管理只有角色调整；超管账号不可被界面改动——保证系统永远有账号能恢复局面。

### 1.2 注册与待分配态

- 注册流程不变（邮箱验证码）。注册成功即 `pending`。
- `pending` 用户登录后：全站只显示一句提示「等待管理员分配权限」+ 退出登录；任何数据接口一律 403。

### 1.3 角色调整规则（等级制，用户 2026-10-20 定稿）

等级：`super_admin`(3) ＞ `admin`(2) ＞ `customer`(1) ＞ `pending`(0)。规则：

1. 只能操作等级**严格低于自己**的用户（不可动平级、不可动上级）；
2. 可赋予的最高角色 = 自己的等级（平级可以"提"，不可以"动"）；
3. 不能操作自己；
4. `super_admin` 角色永不通过接口分配（仅部署配置产生）。

| 操作者 | 可操作对象 | 可赋角色 | 示例 |
|---|---|---|---|
| 超级管理员 | 除自己外所有用户 | admin / customer / pending | 把管理员降为客户 ✓ |
| 管理员 | 仅 customer / pending 用户 | admin / customer / pending | 把客户提为管理员 ✓；把管理员降级 ✗（平级不可动）；设超管 ✗（越级） |
| 客户 / 待分配 | — | — | 无用户管理权限 |

### 1.4 超级管理员的产生

`.env` 配置 `SUPER_ADMIN_EMAIL`，应用启动时幂等地把该邮箱账号提为 `super_admin`（账号不存在则记日志跳过）。按量开关机、备份恢复后每次启动自动自愈，无需人工操作数据库。

### 1.5 客户可见数据与安全边界

- 客户看板 = 现客户视图页：全平台已计入订单明细，字段集与边界沿用 REQ-20261015-02（无任何分类/剔除信息）。客户看板的更多内容后续单独立项补充。
- **权限强制点在后端 API**：内部看板接口仅 admin / super_admin 可调，客户与待分配用户访问一律 403；前端守卫只负责页面导航与入口隐藏。客户即使绕过页面直接调内部接口也拿不到任何数据。

### 1.6 用户管理页

- admin / super_admin 可见：列表（邮箱、昵称、角色、注册时间、最近登录）+ 行内操作（设为管理员 / 设为客户 / 撤销权限）。
- 平级、上级、自己所在行不显示操作入口；后端同时强制规则（前端隐藏仅为体验，不是安全边界）。

## 2. 技术要点

- `users.role` 单列四值 + Alembic 迁移；存量账号迁移后统一落 `pending`，再由 SUPER_ADMIN_EMAIL 机制提权。
- token 不含角色；现有机制每请求查库取用户 → 角色变更对在线用户**即时生效**，无需踢线机制。
- 后端新增 `require_role` 依赖挂在各路由；新增用户管理接口按 §1.3 等级规则判定。
- 前端路由守卫按角色分流 + 收到 403 时重拉 `/me` 自动跳转。i18n en/zh 同步，无图标/emoji。

## 3. 验收标准

1. 新注册用户登录后只见提示页；调任何数据接口返回 403（pytest 断言）
2. 客户角色调内部看板接口（`/summary`、`/orders`、`/orders.csv`、`/sync`、`/sync/status`）全部 403；调客户视图接口（`/customer-orders`、`/customer-orders.csv`）200（pytest 断言）
3. 管理员可将 customer / pending 用户设为 admin / customer / pending；对 admin、super_admin 用户操作返回 403；对自己操作被拒绝；请求赋 `super_admin` 角色不被受理
4. 超管可调整除自己外任何用户（含把管理员降级为客户）
5. 角色变更即时生效：在线用户持有变更前的 token，下一请求即按新角色判定（pytest 断言）
6. 迁移后存量账号为 `pending`；配置 `SUPER_ADMIN_EMAIL` 启动后该账号为 `super_admin`（幂等，重复启动无副作用）
7. 用户管理页列表与操作可用；角色操作在无权限行不出现；文案 en/zh 同步；无图标/emoji
8. 后端 ruff + pytest（含权限矩阵用例）、前端 pnpm lint + build 全过
