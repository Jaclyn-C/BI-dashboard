## 1. 背景与目标用户

### 1.1 背景

- 本项目（Partner Dashboard）的首个需求。现有 `docs/reference/visualisation.html` 为行为规格的单文件看板，正被重构为前后端分离系统；`backend/` 与 `frontend/` 目前均为空目录，本需求将连带两端脚手架初始化（列入第 5 节影响面；脚手架技术细节归 architect 的 DESIGN 文档）。
- 认证体系是后续内部看板的账号入口，也是未来供应商 API 的账号基础。
- 账号统一为**邮箱**（无手机号），邮箱**全局唯一**。

### 1.2 现状行为对照（参考实现 `docs/reference/visualisation.html`）

参考实现的"登录"是对接**上游合作平台**的 `/auth/login`（用上游账号换取上游 token），关键行为：

- `POST /auth/login`，JSON 入参 `{username, password}`，响应含 `access_token`；
- 401 / 403 / 422 → 错误提示 `Invalid username or password.` / 「用户名或密码错误。」（不区分用户名还是密码错）；
- token 存 sessionStorage，后续请求带 `Authorization: Bearer <token>`；
- 任一 API 返回 401 → 清除 token，提示 `Your session expired — please sign in again.` / 「登录状态已过期，请重新登录。」并重新弹出登录卡片；
- 登录卡片 UI：标题 + 副标题 + 用户名/密码输入框 + 错误提示条（`role="alert"`）+ 提交按钮；EN/中文双语；深色模式跟随系统。

### 1.3 本需求与现状的关系

- **账号体系是新建的**：参考实现登录的是上游平台账号（用户名/密码）；新系统登录的是本项目自有账号（邮箱/密码），行为对标但账号数据全新。
- **交互形态对标**：登录卡片风格、双语、深色模式、错误提示文案形态、token 过期重登，均对标参考实现。
- **边界说明**：自建认证与上游 OAuth2（服务端 client-credentials 拉取数据）是两条独立链路，本需求**不改变**上游数据接入方式。

### 1.4 目标用户

- **内部运营**：注册/登录后使用收益看板（看板其余功能由后续需求给出）。
- **下游供应商（未来）**：本账号体系是未来供应商侧能力的账号基础，本需求不实现任何供应商侧功能。

## 2. 功能描述（用户故事）

### US-1 注册

> 作为一名新用户，我希望能用邮箱注册账号，以便之后登录使用看板。

- 注册需提交：**邮箱**（用于接收验证码）+ **昵称** + **密码** + **邮箱验证码**。
- 验证码通过 **SMTP 邮件**发送；SMTP 凭据走 `.env`（发件邮箱账号由用户后续提供）。
- **开发环境降级**：SMTP 未配置时，验证码打印到后端日志，注册流程不中断。
- 注册成功后**自动登录**，直接进入看板。
- 邮箱全局唯一；昵称为显示用途。

### US-2 登录

> 作为一名已注册用户，我希望用邮箱和密码登录，以进入看板。

- 登录凭据：邮箱 + 密码（账号统一为邮箱，无手机号）。
- 登录成功获得会话凭证（token），进入看板；错误提示与过期重登行为对标参考实现（见 1.2）。

### US-3 找回密码

> 作为一名忘记密码的用户，我希望通过邮箱验证码重置密码，以恢复账号访问。

- 需提交：**邮箱** + **验证码**（与注册同一 SMTP 通道，含开发环境日志降级）+ **新密码**。
- 与登录、注册**同期实现**（同一需求、同一交付期）。
- 重置成功后用新密码登录。

### US-4 通用体验

> 作为一名手机或电脑上的用户，我希望认证页面在任何设备上都能正常使用。

- 三个页面（登录/注册/找回密码）视觉风格参考 `visualisation.html` 现有登录卡片设计；
- **必须响应式适配手机和电脑**；
- EN/中文双语；深色模式跟随系统。

## 3. 验收标准（可测试）

依赖待确认默认值的条目已标注对应问题号（Q*），用户修改默认值后按新值验收。

### 注册

- **AC-R1** 注册页提供邮箱、昵称、密码、验证码输入及"发送验证码"操作；邮箱格式非法时前端双语提示，且不触发发码。
- **AC-R2** SMTP 已配置时，触发发码后目标邮箱能收到含验证码的邮件；SMTP 未配置的开发环境，验证码打印到后端日志且注册流程可继续（降级可用）。
- **AC-R3** 验证码正确、密码合规（按 Q1 默认值）、昵称合规（按 Q5 默认值）、邮箱未被占用时：账号创建成功，**自动登录**并跳转进入看板。
- **AC-R4** 邮箱已被注册时：双语提示"邮箱已注册"，不创建新账号。
- **AC-R5** 验证码错误或已过期时：双语提示验证码无效，账号不创建；已过期的验证码再次提交仍被拒绝。
- **AC-R6** 密码不合规时：前端与后端均拦截并双语提示具体规则（按 Q1 默认值）。
- **AC-R7** 同一邮箱在冷却期内（按 Q4 默认值）重复请求发码：双语提示冷却限制，不重复发送。

### 登录

- **AC-L1** 登录页提供邮箱 + 密码；凭据正确时获得会话凭证并进入看板。
- **AC-L2** 邮箱或密码错误时：返回统一的双语模糊提示（对标参考实现 `Invalid username or password.`），不泄露具体是哪一项错误。
- **AC-L3** 未登录状态直接访问看板页面：被重定向到登录页。
- **AC-L4** 会话过期后再操作：提示"登录状态已过期，请重新登录"（对标参考实现），返回登录页，重新登录后可恢复使用。
- **AC-L5**（修订 1 新增）登录成功后**邮箱始终被记住**（下次打开自动填充邮箱）；勾选「记住密码」（默认不勾）并登录成功时，密码一并记住（编码混淆存储于浏览器 localStorage，防肉眼直读、非加密），下次打开自动填充、可直接点击登录；未勾选时仅记住邮箱，密码需手动输入；取消勾选后再登录会清除已存密码。会话 token 仍存 sessionStorage，与记忆行为互不影响。

### 找回密码

- **AC-P1** 找回密码需完整提交邮箱、验证码、新密码三项，缺一不可。
- **AC-P2** 验证码与注册走同一 SMTP 通道（AC-R2 的降级行为同样适用）。
- **AC-P3** 验证码正确且新密码合规时：密码更新成功；旧密码立即无法登录，新密码可以登录；按 Q7 默认值，既有登录态同时失效。
- **AC-P4** 验证码错误或过期时：双语提示，密码不发生任何变更。
- **AC-P5** 未注册邮箱发起找回：双语提示"邮箱未注册"（与注册、登录采用一致的明确提示策略）。
- **AC-P6** 发码频率限制与注册一致（按 Q4 默认值）。

### UI 与通用

- **AC-U1** 登录/注册/找回密码三个页面视觉风格对标参考实现的登录卡片（卡片布局、输入框样式、错误提示条、按钮风格）；EN/中文切换即时生效，无混语。
- **AC-U2** 深色模式跟随系统 `prefers-color-scheme`；明、暗两种模式下认证页面的文字与控件均可读。
- **AC-U3** 响应式：手机窄屏（以 375px 宽为测试基准）与桌面宽屏（以 1280px 宽为测试基准）均能完整走通注册、登录、找回密码全部流程；无横向滚动、无控件遮挡或错位。
- **AC-U4** 所有用户可见文案走 i18n（en/zh 两个 locale 同步维护），无硬编码文案。
- **AC-U5** 网络错误或服务不可用时：双语提示（对标参考实现的 `netError` 行为），不出现未处理的裸错误页面。

### 安全基线（行为层）

- **AC-S1** 密码不以明文落库、不写入任何日志（以单向摘要形式存储，具体算法归 DESIGN）。
- **AC-S2** 验证码不在任何 API 响应体中返回给前端；唯一暴露途径是邮件（开发降级时为后端日志）。
- **AC-S3** SMTP 凭据只存在于 `.env`（`.env.example` 提供占位模板、不含真实值）；代码、日志、迁移、提交中不出现真实凭据。
- **AC-S4** 邮箱全局唯一在数据库层（唯一约束）与业务层（注册查重提示）双重成立。

## 6. 待确认问题列表

以下均为实现级参数或未决业务点，product-agent 无权拍板。每条给出合理默认值，**标注「默认采用，除非用户修改」**；用户确认后 REQ 定稿，验收标准按最终值执行。

| # | 问题 | 默认值建议（默认采用，除非用户修改） |
|---|---|---|
| Q1 | 密码规则 | 长度 8–64 位，至少同时包含字母和数字。（参考实现登录框 `minlength=10` 是上游平台对密码的要求，新系统不沿用） |
| Q2 | 验证码有效期 | 10 分钟；过期作废，须重新发送。 |
| Q3 | 验证码格式与校验尝试上限 | 6 位数字；同一验证码累计校验失败 5 次即作废，须重新发送（防暴力猜解）。 |
| Q4 | 验证码发送频率限制 | 同一邮箱 60 秒冷却期内只能发 1 次；同一邮箱每小时最多 5 封；注册与找回密码共用同一发码通道与限额。 |
| Q5 | 昵称约束 | 2–30 个字符，允许中文、字母、数字、下划线、连字符；仅作显示用途，不要求全局唯一。 |
| Q6 | token 有效期与续期策略 | 不引入 refresh token；access token 有效期 8 小时；到期后按参考实现行为提示"登录状态已过期"并重新登录。 |
| Q7 | 重置密码后的既有登录态 | 密码重置成功后，该账号全部已发放的会话凭证立即失效，须重新登录。 |
| Q8 | 账号角色体系 | 本期所有注册账号为同等权限的普通账号，不做角色/管理员区分；角色体系留待后续需求。 |
| Q9 | 验证码邮件的语言 | 邮件正文采用中英双语并列（与产品双语定位一致，不依赖触发时的界面语言）。 |
