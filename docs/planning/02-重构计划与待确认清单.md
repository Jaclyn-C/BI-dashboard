# 重构计划与待确认清单

> 日期：2026-10-12
> 前置阅读：`../research/01-调研发现与逆向分析.md`
> 结论先行：**过滤规则之外的 ~80% 模块现在就可以开工**；规则本身单列为可插拔点，等确认后接入。

---

## 0. 硬性约束（红线，全项目适用）

1. **新系统运行时只允许调用上游飞书文档内的 8 个接口**（当前实际需要其中 3 个：`/open/oauth2/token`、`/open/order/list`、`/open/order/adSummary`）；
2. **前开发自建的 2 个接口（`/auth/login`、`/data/partner/order/report`）不得作为依赖调用，逻辑全部由我方重写**；
3. 上游 client_id/client_secret **只存新后端服务端**，任何情况下不得下发到浏览器/供应商端；
4. 逻辑已能推断的模块 → 立即重构；推断不出的 → 记入 §3 待定清单，等业务确认后再实现，不猜测、不臆造。

---

## 1. 目标架构

```
供应商 / 看板前端
      │ HTTPS（只访问我方后端）
      ▼
┌─────────────────── 新后端（我方自研）───────────────────┐
│ ① 鉴权服务        /auth/login 等（自写，兼容老契约）      │
│ ② 上游客户端      OAuth 换票/缓存/续期；窗口化拉单+二分补全 │
│ ③ 订单接入管道    全量拉取 → 字段规范化 → 落库            │
│ ④ ★分类器        classify(order) → included|excluded     │
│    （可插拔：规则实现待确认后接入，见 §3 B1）              │
│ ⑤ 报表服务        替代 /data/partner/order/report（真分页）│
│ ⑥ 广告收入代理    /open/order/adSummary 服务端代理        │
│ ⑦ 聚合/结算引擎   20%/70% 分成、按日/币种/国家聚合         │
└──────────────────────────┬──────────────────────────┘
                           │ 仅此一条出站依赖
                           ▼
              上游 netshort CPS（飞书文档 8 接口）
```

设计要点：**分类器 ④ 是全系统唯一的"缝"**。上游客户端、接入管道、报表、聚合引擎都只依赖"订单 + 分类标签"，不关心分类怎么来的。

## 3. B 清单：推断不出、暂缓实现（等确认）

| # | 事项 | 缺什么 | 等谁 | 期间怎么办 |
|---|---|---|---|---|
| B1 | **订单分类规则**（核心黑盒） | 判定"哪些订单计 20% / 哪些计 70%"的规则。已确定：确定性、与所有可见属性无关、与退款概率相关、稳定 ~80/20；推测是上游归属/结算口径 | 问题 1（netshort）/ 问题 2（业务）/ 问题 3（前开发） | 分类器接口先建好、留空实现；新系统先出"全量订单"，供应商端如何呈现由业务定 |
| B2 | 70% 档合同口径 | 什么订单适用 70%、结算追溯方式 | 业务/合同 | A7 引擎把比例做成配置项（20/70 只是当前值） |
| B3 | 历史数据迁移口径 | 历史订单的已计入/被剔除以什么为准 | 与 B1 同源 | 记录器（§4 Phase 0）持续留档，历史真值随时间固化 |
| B4 | 供应商账号迁移 | 现有账号清单、密码体系 | 业务/前开发 | 新鉴权服务先支持建号，迁移脚本后补 |
| B5 | `createTime` 时区 | 上游时间戳时区（分析显示疑似 UTC 且有滞后） | netshort | 接入管道按"上游原值"存，展示层再定时区，不在存储层猜 |

**明确不做臆造**：B1 在确认前，任何人不得用猜测的规则填充分类器——宁可使报表暂出全量，也不出错误的 20/70 金额（金额直接牵涉结算）。

## 4. 分阶段计划

**Phase 0 —— 数据记录器（本周可做，很小，但优先级最高）**
- 每日定时拉取并落库：上游 `/open/order/list` 全量 + 老 `/data/partner/order/report` 报表，逐笔保存分类标签；
- 目的：①老后端随时可能下线，**它每多跑一天，我们就多一天带正确标签的历史真值**；②标签攒够可用于离线拟合规则（可能不用等上游答复）；
- ⚠️ 依赖待确认问题 4（调研期是否允许继续查询老后端）。若不允许，则只录上游全量，放弃标签（损失 B3 真值，需业务知情）。

**Phase 1 —— A 清单并行开发**（A1→A2→A5 打通数据链路；A3/A4/A7/A8/A9 并行；A10/A11 收尾）
- 里程碑：新后端能以自有账号体系输出与老后端同契约的"全量订单报表" + 广告收入 + 聚合看板（class 列暂空）。

**Phase 2 —— 规则接入与切换**（B1 确认后）
- 实现分类器规则版 → 用 A10 对账工具与老后端逐单比对（老后端仍在运行的前提下 100% 一致才切换）→ 供应商灰度 → 下线老后端依赖。

---

## 5. 验收方案

1. **逐单一致性**（B1 到手后）：同日期段，新旧系统输出做 `tools/export_diff.py` 比对，要求订单集合、分类、金额、状态 0 差异；
2. **契约兼容性**：`/data/partner/order/report` 与老契约逐字段兼容（分页行为改善除外，需在变更说明中告知供应商）；认证已定稿为新体系（`/api/v1/auth/**`、邮箱账号，不做老契约 shim，仅保留 `access_token` 响应键名——见 REQ-20261012-01 与 DESIGN-20261012-01）；
3. **安全验收**：仓库与前端产物中 grep 不到任何 client_secret / 密码；浏览器网络面板仅见我方后端域名。

## 6. 风险与依赖

| 风险 | 影响 | 缓解 |
|---|---|---|
| 老后端突然下线 | B1/B3 真值永久丢失 | Phase 0 记录器立即上线 |
| 上游不提供归属字段 | B1 无法原生复现 | 数据拟合路线（记录器标签）+ 业务重定义规则（实现 C） |
| 20/70 金额牵涉结算 | 错误规则=错误钱 | B1 确认前不输出分类金额 |
| 上游接口限流未知 | 高峰拉取可能被限 | 窗口化 + 并发度做成配置；观察期记录 429/超时 |
| 供应商已按老口径对接 | 分页行为变化影响调用方 | 契约尽量兼容，变更提前通知 |
